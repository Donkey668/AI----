## User Scenarios & Testing *(mandatory)*

### User Story 1 - 在新项目中使用原有功能 (Priority: P1)

作为原型用户，我希望在新项目中继续使用原型已有的功能，保持操作流程、数据规则和结果语义一致。

**Why this priority**: 首期目标是等价迁移，新增功能或重设计不能替代迁移完成。

**Independent Test**: 对一个现有功能在原型和新项目中执行相同输入、初始状态和操作，比较结果与状态变化。

**Acceptance Scenarios**:

1. **Given** 已盘点并记录原型功能与行为，**When** 用户在新项目执行相同操作，**Then** 功能入口、交互流程、计算规则及结果语义与基准一致。
2. **Given** 原型包含登录限制、数据持久化和导出规则，**When** 新项目执行对应操作，**Then** 权限、数据归属、保存与导出行为保持一致。
3. **Given** 原型对无数据、无效输入或服务失败已有处理，**When** 新项目遇到相同条件，**Then** 保持对应的提示和状态处理，不静默替换规则。

### User Story 2 - 按章程验证与交付迁移结果 (Priority: P1)

作为项目负责人，我希望新项目满足既定架构和多端方向，同时能先在浏览器验证迁移后的功能。

**Why this priority**: 既要完成技术栈转写，也要保持快速可验证的开发路径。

**Independent Test**: 独立启动前后端，在浏览器完成原型功能回归；平台集成时另行验证各容器运行结果。

**Acceptance Scenarios**:

1. **Given** 新项目已按章程组织，**When** 不启动桌面或手机容器，**Then** 用户仍能在浏览器验证共享业务功能及前后端联调。
2. **Given** 本轮前后端迁移已完成，**When** 进行本轮验收，**Then** 在浏览器验证全部原型功能，不要求交付 Electron 安装包或手机套壳应用。

### User Story 3 - 在必要逻辑变更之前获知并决策 (Priority: P1)

作为项目负责人，我希望任何无法避免的逻辑变更先向我说明，避免迁移过程中擅自改变原型行为。

**Why this priority**: 用户明确要求保持实现逻辑，并保留必要变更的决策权。

**Independent Test**: 审查一个已识别的迁移阻碍及变更记录，确认用户决策之前没有实施或试改相关逻辑。

**Acceptance Scenarios**:

1. **Given** 发现无法保持原逻辑的具体阻碍，**When** 尚未得到用户决定，**Then** 先说明原逻辑、阻碍证据、影响范围和可选方案，不尝试改动相关逻辑。
2. **Given** 某局部逻辑变更等待决定，**When** 仍有不受影响的迁移工作，**Then** 可以继续这些独立工作，并明确阻塞范围。

### Edge Cases

- 原型无法启动、缺少依赖或外部服务不可用：记录阻碍及未验证范围，不将不可验证表述为等价通过。
- 原型存在缺陷或占位功能：如实记录并保留实际行为，不在迁移中擅自修复或补全。
- 外部实时数据或模型输出不确定：采用相同受控输入与服务响应比较规则和结果结构，不要求实时文本逐字相同。
- 框架运行差异影响登录、存储、路由或文件访问语义：先分析能否等价适配；确需改变逻辑时先告知，未经用户决定不得试改。
- 原型在盘点后发生变化：继续使用已锁定提交，不静默引入后续提交、未提交修改或未跟踪文件；更换基准须由用户明确决定。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 原型唯一指定来源为 F:\VibeCoding\watch_the_bird，迁移结果写入当前项目 F:\AI观鸟助手；不得修改原型作为迁移手段。
- **FR-002**: 迁移基准锁定为原型最近一次 Git 提交 9ba9f18e18e29826ac6fc6694b5a873d015bbdf8（ENDFIELD v2.6）。必须依据该提交盘点已有功能、入口、规则、数据和外部依赖，不得纳入工作区未提交修改、未跟踪文件或后续提交，也不得仅依据历史规格或开发文档判断已实现内容。
- **FR-003**: 首期范围为原型当前已实现功能的等价转写；开发文档中尚未实现的能力不自动纳入首期。
- **FR-004**: 必须保留原项目实现逻辑，包括算法与计算参数、校验规则、状态转换、权限和会话语义、数据归属与持久化规则、外部服务请求及响应处理、异常与降级规则。
- **FR-005**: 必须保留现有界面内容、交互流程与响应式行为；技术迁移不能成为重新设计或删减功能的理由。
- **FR-006**: 技术栈、前后端分离、共享前端和多端交付方向必须符合项目章程；必要的构建、路由和运行适配仅在保持业务逻辑与行为等价时执行。
- **FR-007**: 若确有不得不改变实现逻辑的地方，必须先报告原逻辑、原因、证据、影响及可选方案，并等待用户明确决定；不得在告知前或等待期间尝试相关逻辑改动。
- **FR-008**: 不得借迁移新增业务功能、改变产品规则、替换算法或修复原型逻辑缺陷；发现问题须记录并单独告知。
- **FR-009**: 必须提供可在浏览器运行的迁移结果及启动说明，浏览器验证不得依赖先完成容器打包。
- **FR-010**: 每项基准功能必须有对应的迁移位置、等价验证结果或明确阻塞说明；未验证项不得计为通过。
- **FR-011**: 缺少依赖导致首选方案受阻时，遵守章程的先告知要求，不得静默使用劣等备选方案。
- **FR-012**: 必须识别并记录迁移前后数据兼容性和存储位置差异；不得擅自迁移、覆盖或删除原项目真实用户数据，不得将原型私密配置写入规格或版本库。
- **FR-013**: 本轮交付范围为前后端迁移及浏览器等价验证；Electron 桌面端集成、安装包和手机套壳应用均留到后续阶段，不作为本轮完成条件。
- **FR-014**: 本轮不复制或迁移原型现有账户与观测记录，新项目使用隔离的测试数据和存储验证原有账户、权限及记录规则，不得写入原型的数据存储。
- **FR-015**: 根据用户后续明确授权，识别与百科模型改为 qwen3.8-flash，使用指定的北京兼容接口；后端流式调用并保持网页原有功能和 JSON 响应。每次只提交当前上传图片或本次识别出的鸟名与固定格式指令，不携带历史图片、对话、回答或思考内容；该授权覆盖 FR-004 的原模型调用配置保留要求。

### Key Entities

- **迁移基准**：原型路径、锁定提交编号、盘点日期和该提交的已实现功能清单；工作区差异不属于迁移来源。
- **行为对照项**：原型功能、前置状态、输入与操作、预期输出、迁移对应位置和验证状态。
- **逻辑变更请求**：原行为、阻碍证据、拟变更内容、影响、用户决定和落实状态。
- **验证记录**：环境、验证场景、实际结果、通过状态及外部依赖造成的限制。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 原型盘点范围内的功能 100% 有迁移与验证对照记录，无未说明的功能遗漏。
- **SC-002**: 在相同初始状态、输入和受控外部响应下，全部已完成迁移的基准场景通过等价验证；存在未通过或受阻场景时不得宣称完整迁移完成。
- **SC-003**: 未经用户明确决定的业务逻辑变更数量为 0；所有必要逻辑变更均先告知、后决策、再实施。
- **SC-004**: 所有共享业务场景均能直接在浏览器验证，前期验证不以桌面或手机打包为前提。
- **SC-005**: 原型目录因本次迁移产生的文件修改数量为 0。

## Assumptions

- 先前通过工作区只读观察到的模块仅作为初步线索；完整功能范围和行为必须重新依据锁定提交盘点，不能把工作区观察直接当作提交内容的证明。
- 技术栈以项目章程为准，框架转写本身已获授权；该授权不包含业务逻辑变更。
- 首期仅交付前后端迁移及浏览器等价验证；桌面与手机容器在后续阶段按章程推进，不将未经验证的平台标记为完成。
- 本轮历史账户与观测记录迁移不在范围内；使用独立测试数据，保持原型真实数据不动。
- 外部服务、必要配置和依赖是完整验证的前提；缺失时明确列出阻碍，不编造验证结果。
- 用户在实施阶段明确将真实外部服务联调延期；本地交付记录受控验证结果和未联调项，保持 SC-002 对最终完整验收的限制。
